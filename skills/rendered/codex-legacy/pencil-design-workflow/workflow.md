# Pencil 设计先行工作流

本流程用于 Pencil / `.pen` / pencli 相关的设计先行任务。它是工具链路由和设计交付流程，不是通用前端实现流程。

## 1. 判断是否触发

应使用本流程：

- 用户说“做设计图”“做设计稿”“先做设计”“先出方案确认”。
- 用户说“mockup”“wireframe”“prototype”“视觉稿”“可视化草图”。
- 用户表达“我确认设计以后再写代码”“先别写代码，先看看效果”。
- 用户明确提到 Pencil、pencli、Pencil CLI、`.pen`、Pencil MCP、Pencil Desktop、Pencil 画布。
- 用户要求审查 `.pen` 设计稿、Pencil 导出图，或对照 Pencil 设计检查前端实现。

不应使用本流程：

- 修已有 UI 的明确局部错误，例如按钮颜色、padding、hover、label 对齐、文字溢出。
- 直接修改已有前端实现中的小样式 bug。
- 根据已有设计稿直接实现代码，而不需要生成或审查 Pencil 设计产物。
- 单纯 review React/Vue/Svelte/Tailwind 代码或真实网页截图；这类优先由 `global-frontend-design` 或普通代码流程处理。

判断标准：目标是“创建/探索/确认设计产物”时使用；目标是“修已有实现里的明确问题”时不使用。

## 2. 明确输出目标

开始前按需确认：

- 新建设计，还是迭代已有 `.pen`。
- 是否需要用户实时看设计过程。
- 是否只需要无头生成和导出图。
- 是否需要审查 `.pen` / 导出图 / 设计到代码的一致性。
- 设计确认后是否进入真实前端实现。

如果用户要求先设计确认后写代码，设计确认前不要进行大规模代码实现。

## 3. 选择运行模式

优先级：

1. 需要用户看设计过程：优先 Pencil Desktop + MCP。
2. 用户明确当前 VS Code / Cursor 插件画布就是目标：可用 VS 插件谨慎模式，并先确认 active `.pen`。
3. 批量生成、不需要看过程、自动化、CI 或 headless：使用 Pencil CLI。

VS 插件多窗口环境下不要默认认为 MCP 指向当前可见窗口。无法确认目标画布时，先让用户切换到 Pencil Desktop 或指定 `.pen`。

## 4. 保存设计产物

默认保存到项目内：

```text
designs/pencil/<slug>/
```

使用 `references/file-locations.md` 的命名规则。不要把可交付设计文件放到临时目录。

## 5. 生成、迭代和展示

Pencil MCP 模式：

- 用 MCP 工具读取当前编辑器状态、布局和截图。
- 分批修改：先结构，再变量和视觉细节。
- 用截图或导出图向用户展示结果。

Pencil CLI 模式：

- 使用用户确认过的 prompt，不擅自扩写视觉细节。
- 生成 `.pen` 的同时导出 PNG/PDF。
- 命令可能运行数分钟，应给足超时时间。
- 命令完成后读取导出图并展示给用户。

## 6. 审查场景

当用户要求 Claude Code 审查 Pencil 相关产物时：

- 设计稿审查：检查视觉方向、文字重叠、字体渲染、裁切、层级、状态覆盖和响应式设计意图。
- 设计到代码审查：对照 Pencil 导出图和前端实现 diff，标注偏离、缺失状态、token 不一致和真实浏览器验证缺失。
- PR/UI diff 审查：如果变更涉及 `.pen`、导出图或设计先行产物，把 Pencil 截图和导出文件作为证据。

审查输出使用 `templates/review-report.md`。

## 7. 交接到前端实现

用户确认设计后，如需写真实前端代码：

1. 记录已确认的设计产物路径和导出图。
2. 将实现阶段交接给 `global-frontend-design`。
3. 按项目现有前端栈、组件、token、路由和验证命令落地。
4. 不把 Pencil 画布验证说成真实浏览器验证。

真实网页视觉验证需要 Playwright、浏览器 MCP 或人工浏览器检查；当前 Claude Code 真实前端视觉自检需要补 Playwright/浏览器 MCP。
