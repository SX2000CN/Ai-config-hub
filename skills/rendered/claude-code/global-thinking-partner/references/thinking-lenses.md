# 思维镜头

## 方案发散

目的：防止 agent 直接采用第一个看似可行的方案。

可问：

- 最小改动方案是什么？
- 更稳健但成本更高的方案是什么？
- 如果未来还要扩展，当前方案会不会卡住？
- 是否存在“不做新功能，只调整流程/规则/文档”的替代路径？

输出时不要列太多方案；通常 2-3 个足够。

## 失败模式

目的：提前暴露当前方案的边界和隐含假设。

可问：

- 哪个前提如果不成立，方案会失效？
- 数据、权限、并发、路径、环境、平台差异会不会导致问题？
- 自动化是否可能误触发、误覆盖、误同步？
- 文档和实际行为是否可能漂移？

失败模式应配一个最小缓解动作，而不是只制造担忧。

## 简化路径

目的：避免为了“看起来完整”而过度设计。

可问：

- 这个抽象现在真的需要吗？
- 能不能先用规则、模板或手动触发，而不是 hook / daemon / 自动同步？
- 是否可以删掉兼容层、配置项或重复事实源？
- 三个相似文件是否真的需要统一框架？

简化不等于偷懒；目标是减少未来维护成本。

## 维护者视角

目的：让后续人类或 AI 能理解当前决策。

可问：

- 文件路径和命名是否暴露了真实事实源？
- 文档是否说明了已完成、待确认和残留风险？
- 下一位接手者能否知道该读哪里、不要重复什么？
- 输出是否区分事实、推断和建议？

维护者视角应优先关注概念边界和接手成本。
