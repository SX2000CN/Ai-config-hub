# 产品级 UI 工程

在已经选择视觉方向后，使用本参考把它落到可维护、可操作、状态完整的产品界面。

## 基本关系

视觉方向是主张，产品 UI 工程是约束和落地方式。不要为了复用和一致性把视觉方向抹平；也不要为了视觉效果牺牲理解、可访问性和真实状态。

## 信息层级

每个界面都应让这些问题一眼清楚：

- 这个界面是做什么的？
- 用户第一步应该做什么？
- 哪些信息是主要内容、次要内容或元信息？
- 哪些操作是安全、次要、危险或不可逆的？
- 系统当前处于什么状态？

用尺寸、字重、对比、位置、分组和动效表达优先级。层级应该承接已选视觉方向，而不是套一套通用卡片布局。

## 布局节奏

保持界面节奏稳定：

- 页面边距和最大宽度。
- 区块间距。
- 卡片内边距。
- 控件高度。
- 图标尺寸。
- 行高。
- label 与控件间距。
- 标题与正文间距。

高密度界面可以很好，但密度必须是有意识且一致的。

## 组件边界

在当前就有价值时再创建组件：

- 重复的视觉结构。
- 清晰的领域概念。
- 值得隔离的有状态交互。
- 不应反复手写的可访问性模式。

不要仅因为代码出现两次就抽象；如果抽象隐藏了重要上下文，就先保留直观结构。

## 产品状态

生产 UI 不能只展示 happy path。按需处理：

- 无数据、筛选后无数据、部分数据。
- 慢加载、加载失败、可重试。
- 校验失败、保存中、成功确认。
- 权限不足、操作不可用、危险操作确认。
- 超长内容、异常数字、极小屏幕。

详细状态和响应式覆盖见 [responsive-state-coverage.md](responsive-state-coverage.md)。

## 文案和可操作性

UI 文案应减少不确定性：

- 按钮文案描述具体动作。
- 空状态解释为什么为空，以及下一步能做什么。
- 错误提示说明问题和恢复方式。
- 危险操作明确后果。

能用具体动词时，避免只写“提交”这类泛化 CTA。
