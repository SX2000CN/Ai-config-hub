# 工作流

非简单前端 UI 工作使用本流程。局部 UI bugfix、小样式修复、文字溢出、按钮对齐、已有设计直接实现或后端/文档任务，不使用本流程。默认顺序是：先确定产品化视觉立场，再把它落到现有代码库；只有用户明确要求设计图、mockup、wireframe、`.pen` 或先设计确认时，才转交 `pencil-design-workflow`。

## 1. 理解产品时刻

修改前先明确目标：

- 路由、页面、组件、截图或文件路径。
- 用户目标和主操作。
- 受众、使用场景和情绪预期。
- 现有品牌、产品语气或用户指定的视觉方向。
- 用户需要的是实现、review、设计建议还是实施计划。

如果受众、目标或视觉语气会实质影响 UI，但当前信息缺失，应先问一个聚焦问题。

如果用户明确提出“做设计图”“先做设计”“先设计确认后写代码”、mockup、wireframe 或 `.pen`，先交给 `pencil-design-workflow` 产出 Pencil MCP 画布证据。没有可见画布证据前，不进入大规模前端实现，也不用代码草图替代设计稿；普通前端实现或局部修复不因此自动启动 Pencil。

只有用户明确要求后台、无头、批量、自动化或不需要看过程时，才允许由 `pencil-design-workflow` 使用 CLI/headless。

## 2. 命名视觉方向

在规划布局和代码前，先选择一个清晰方向。方向应能用一句话命名，例如：

- 高密度企业指挥中心。
- 安静的编辑部式研究工作台。
- 柔和消费级 SaaS 引导流程。
- 精密工业控制面板。
- 轻快、有触感的创作工具。
- 克制、高级、低噪音的数据产品。

不要默认使用白底渐变、圆角卡片、通用三栏 CTA 或随机装饰 blob。除非产品语境确实需要，否则不要做安全但没有记忆点的模板 UI。

复杂或模糊的 UI 工作，先使用 [templates/ui-brief.md](templates/ui-brief.md)。

## 3. 让方向可见

在进入实现前，说明 3 到 5 个具体视觉动作：

- 字体：字号阶梯、字重、展示字体或数字样式。
- 颜色：主表面、强调色、语义状态和对比度。
- 空间：密度、留白、分组、卡片内边距和页面节奏。
- 构图：网格、分栏、非对称、叠加或高密度布局。
- 表面：边框、阴影、纹理、渐变、噪点、图案或刻意扁平。
- 动效：一个有目的的高影响瞬间或状态过渡。

这些动作必须服务理解、层级、操作信心或产品记忆点。降低可读性和可操作性的视觉效果应删除。

## 4. 检查项目现有约定

把视觉方向落地前，检查并尊重项目约定：

- 框架和路由方式。
- 样式体系：CSS、CSS modules、Tailwind、CSS-in-JS、设计 token、主题变量。
- 组件库和已有共享组件。
- 表单、弹窗、表格、导航、toast 等模式。
- 数据加载和错误处理模式。
- 现有验证命令和开发服务器命令。
- 相关 README、设计系统文档或项目 AI 状态文件。

除非明确缺失或不适合当前需求，否则优先沿用已有约定。沿用不等于抹平视觉方向，应在现有 token、组件和布局约束内做出清晰选择。

## 5. 规划产品 UI 结构

定义：

- 信息层级：用户第一眼看什么，下一步做什么。
- 页面区域和组件边界。
- 主要、次要、危险和不可逆操作。
- 状态模型：loading、empty、error、success、disabled、focus、selected、长内容、权限受限等。
- 响应式行为：按断点或布局模式说明。
- 交互模型：键盘、鼠标、触控和 reduced motion。
- 哪些复用，哪些新建。

较大的改动使用 [templates/implementation-plan.md](templates/implementation-plan.md)，但实施计划应引用或总结前面的视觉 brief。

## 6. 按项目原生模式实现

规则：

- 做满足目标的最小完整改动。
- 优先复用已有组件和 token。
- 除非用户要求或项目已有依赖，不新增依赖。
- 不为假想未来场景创建抽象。
- 视觉细节必须服务已选方向，不堆装饰。
- 只在系统边界验证用户输入和外部数据，不为框架保证的内部不变量增加多余防御。

## 7. 验证

运行最小相关验证：

- 类型检查、lint、单元/组件测试、构建或 Storybook，按项目实际情况选择。
- 涉及 UI 修改时，能启动开发服务器就实际在浏览器查看目标界面。
- 检查视觉方向是否真实可见，而不只是文档里写了主题。
- 检查桌面和移动端布局。
- 按需检查 loading、empty、error、disabled、hover、focus、长内容等状态。
- 检查控制台错误。

详见 [references/verification.md](references/verification.md)。

## 8. 汇报

最终回复应包含：

- 改了什么。
- 应用的视觉方向和关键视觉动作。
- 更新了哪些文档，或为什么无需更新文档。
- 运行了哪些命令或浏览器检查。
- 已知限制或残留风险。

较大的 UI 工作可使用 [templates/final-report.md](templates/final-report.md)。
