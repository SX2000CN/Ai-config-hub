# 思维伙伴工作流

目标：在动手前或方案不确定时，用短、准、低副作用的方式扩展思考，而不是替代主工作流执行任务。

## 1. 判断是否值得触发

触发和退出边界以 `references/trigger-boundaries.md` 为唯一权威，判断前先读它，这里不重复列举。

不满足时，直接返回主工作流，不要增加噪音。

本 skill 只做低副作用思维扩展，不自动拉起项目配置、脉络、前端设计、验证或实现流程；推荐方向应回到主任务路由。

## 2. 固定四个镜头

按需选择 1-4 个镜头，只选真正对当前任务有实质观察的镜头；如果只有一个镜头有真实内容，只输出这一条，不为了凑数量硬填另一条：

1. 方案发散：还有哪些路径？最小改动、稳健方案、长期方案分别是什么？
2. 失败模式：这个方案在哪些边界、假设或未来变化下会失败？
3. 简化路径：能否用更少概念、更少文件、更少自动化完成？
4. 维护者视角：后续人类或 AI 接手时，命名、边界、文档和验证是否清楚？

## 3. 输出约束

输出条数等于选中的镜头数（1-4 条），只按 `templates/thinking-brief.md` 的格式逐条输出，不写长篇论文，也不额外展开观察/影响/建议这类分段结构。

每条按镜头名称给一句话结论，包含足够信息判断影响和下一步，而不是只列现象。如果用到了项目文件作为依据，在对应那一条里直接点出文件或位置，不单独开一个"依据"字段。

避免：

- 泛泛的“加强测试”“注意安全”。
- 没有当前项目语境的抽象建议。
- 把建议写成已决定的计划。
- 在用户未确认前要求大范围重构。

## 4. 低副作用边界

默认不修改文件，不运行会改变状态的命令，不创建提交，不同步全局目录。

如果确实需要读取项目文件来理解上下文，只读即可；依据文件按 §3 的方式在对应结论里点出，不单独罗列。

如果用户明确要求进入实现阶段，应退出本 skill 的思维扩展模式，转入正常计划和实现流程。

## 5. 结束条件

输出应以一个推荐方向收束：

- “推荐先走最小方案，因为……”
- “推荐先补一个验证点，因为……”
- “推荐暂不新增抽象，因为……”
- “推荐进入实现前先确认一个问题：……”

不要留下过多开放分支。
