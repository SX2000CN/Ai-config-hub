# 全局 AI 编码规则

> 同一套核心规则应尽量同时适用于 Claude Code、Codex 和其他 AI 编码工具。工具专属机制放在各自补充段，不混入通用核心。

## 1. 核心目标：代码、配置、文档保持一致

默认把项目文档视为项目的可读索引和事实来源。对于长期维护项目、多人协作项目、生产项目和私有维护项目，代码、配置、部署、数据库、接口、用户流程或核心行为发生实质变化时，必须同步评估并更新相关文档。

目标是：任何人、任何 AI 编码工具、任何后续维护者，只要阅读项目中的文档，就能准确理解项目的当前状态、架构、功能、运行方式、部署方式、核心流程、已知限制和后续计划。

对于临时实验、小型脚本、格式化、局部变量重命名、内部无行为变化重构、测试内部实现调整、生成文件变动等不影响项目理解和使用方式的修改，可以不更新文档，但最终回复中应说明无需更新文档的原因。

如果用户明确要求只做临时代码实验或只做一次性验证，可以暂不更新长期文档，但必须在回复中说明这是临时例外。

## 2. 工作前按需理解项目

开始修改前，按任务复杂度快速查找并阅读相关说明文件，例如：

- `AGENTS.md`
- `AGENTS.override.md`
- `CLAUDE.md`
- `README.md`
- `docs/`
- `CHANGELOG.md`
- `PRIVATE_PROJECT.md`
- `.github/instructions/`
- 当前模块目录下的说明文档

小型局部修改只需阅读最相关的文档和代码；跨模块、配置、部署、数据库、API、用户流程或架构变更，则必须阅读项目级文档和相关模块文档。

如果文档和代码冲突，不要盲信文档；以代码、实际配置、运行结果和用户当前说明为准，并在必要时修正文档或在回复中指出差异。

## 3. 文档更新规则

代码、配置或流程变更必须同步评估文档影响。只要变更影响以下任一内容，就必须更新相关文档：

- 项目用途、产品定位、用户流程
- 架构、目录结构、模块职责
- API、IPC、CLI、路由、事件名、数据流
- 数据库表结构、迁移、字段含义
- 配置项、环境变量、密钥使用方式
- 构建、测试、运行、部署、发版流程
- 依赖、技术栈、版本要求
- 重要功能状态：已完成、部分完成、未开始、已废弃、计划中
- 关键限制、风险、注意事项、排障方式

如果变更不影响用户可见行为、接口、配置、部署、数据结构、运行方式或长期维护信息，可以不更新文档，但最终回复需说明原因。

不要为了满足文档要求创建低价值文档；优先更新已有、会被维护者实际阅读的文档。

如果项目缺少文档索引，且本次变更影响项目理解、运行、部署、API、配置或核心流程，应优先更新现有文档；没有现有文档时，可以建议或创建合适的索引文档，例如 `README.md`、`docs/README.md` 或 `docs/项目索引.md`。

## 4. 文档必须描述真实状态

文档不能写成愿景替代现实。必须明确区分：

- 已完成
- 部分完成
- 未开始
- 计划中
- 已废弃
- 暂时方案
- 推断信息

不要夸大完成度。不要写“已完成”来描述代码中尚不存在的能力。

如果某个信息来自推断，而不是代码、配置、运行结果或用户明确说明，必须标注为推断。

## 5. 项目文档应覆盖的内容

项目文档应尽量让后续工具快速理解：

- 项目是什么，解决什么问题
- 技术栈和主要子系统
- 目录结构和关键文件职责
- 本地开发、构建、测试、部署命令
- 核心数据流、任务流、用户流程
- API、IPC、事件、数据库表、配置项、环境变量
- 当前功能完成度
- 已知风险、限制和后续计划
- 重要设计决策及原因
- 发版、运维、排障注意事项

文档应清晰、准确、可验证：

- 使用明确的文件路径、入口函数、命令和配置名
- 不重复粘贴大段代码，只解释结构、流程和约定
- 长期文档可以包含“最后更新时间”或“最后核验时间”；仅当项目已有该约定，或文档内容发生实质更新时同步更新
- 阶段性文档必须标注当前进度
- 文档中的命令应尽量可直接执行
- 中文项目优先使用中文说明，除非项目已有英文规范
- 不保留已经过期的旧流程，除非明确标为历史记录

## 6. 敏感信息默认规则

默认不要把真实密钥、私钥、Token、服务器密码、支付密钥、数据库密码、生产凭证等敏感信息写入普通项目文档、代码注释或示例配置。

即使项目是私有项目，也优先记录凭证用途、环境变量名、配置位置、获取方式、轮换方式和占位符，不记录真实值。

只有当用户在当前任务中明确确认“这是私有项目，可以记录真实凭证”，并确认该文档不会公开、共享、截图或上传时，才允许把真实凭证写入专门的私有凭证文档，例如：

- `docs/private/凭证与密钥.md`
- `docs/deploy/凭证与密钥.md`
- 项目已有的私有运维文档

写入真实凭证时必须遵守：

1. 在相关文档顶部写明：`本项目未开源，文档可能包含真实凭证，仅限私有维护使用。公开、共享、截图或上传前必须清理敏感信息。`
2. 密钥、Token、服务器账号、支付配置等应集中记录，不要散落在 README、架构文档、部署文档、代码注释等多个位置。
3. 普通说明文档可以引用“见凭证文档”，不要重复粘贴完整密钥。
4. 修改相关配置、服务、域名、支付、部署流程时，必须同步检查凭证文档是否过期。
5. 如果项目未来准备开源、交给第三方、上传公开仓库、发布截图或导出文档，必须先清理真实凭证，并建议轮换已暴露凭证。

如果用户明确说明项目未开源，而仓库中没有私有声明，应建议创建 `PRIVATE_PROJECT.md`。

## 7. 工具、权限与自动化

遵守当前工具的审批、沙箱和权限机制。不要绕过权限、跳过 hooks、禁用验证、强制推送、删除未确认数据或执行高风险命令，除非用户明确授权。

自然语言规则只负责指导行为；如果某个行为必须自动执行，应使用对应工具的配置、hooks、settings、config 文件或 CI 机制实现。

不要把某个工具的专属能力当成所有工具都支持。使用 IDE 插件时，可以利用当前文件、选区、诊断信息和 diff 能力，但修改前仍应以实际文件内容为准。

全局规则只规定通用工作方式，不应包含某个具体项目的架构、路径、命令、服务名或业务事实；项目事实应放在项目内文档。

## 8. 修改代码时的检查清单

实现或修复时，持续检查：

- 这个变更是否改变了用户可见行为？
- 是否改变了 API、IPC、CLI、路由或事件？
- 是否改变了配置、环境变量或密钥使用方式？
- 是否改变了数据库结构或数据含义？
- 是否改变了部署、构建、测试或发版流程？
- 是否新增了页面、模块、服务、任务流或数据流？
- 是否让已有文档中的描述过期？

只要答案是“是”，就同步更新文档。

修改代码、配置或脚本后，应优先运行项目已有的最小相关验证，例如 lint、typecheck、单元测试、构建、脚本自检或 dry-run；如果因环境、耗时、依赖缺失或权限限制无法运行，应在最终回复中说明原因和替代检查。

## 9. 完成工作后的回复要求

对涉及文件修改、配置修改、脚本执行或项目状态判断的任务，最终回复中应简要说明：

- 改了哪些代码或配置
- 更新了哪些文档
- 如果没有更新文档，说明原因
- 运行了哪些验证命令
- 是否还有文档和代码不同步的残留风险

## 10. 优先级

项目内更具体的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`、模块文档或用户当前明确要求，优先于本全局规则。

如果项目内规则与全局规则冲突，遵循项目内规则；如果项目内规则明显过期，应以代码和实际配置核实，并在回复中指出。

“代码、配置、文档保持一致”始终是默认要求，除非用户明确要求只做临时代码实验。

## Codex 专用补充

- 全局个人规则维护在 `~/.codex/AGENTS.md`；如存在 `~/.codex/AGENTS.override.md`，其优先级更高。
- 项目级规则优先维护在项目内 `AGENTS.md`；如存在 `AGENTS.override.md`，其优先级更高。
- 如果项目同时维护 `CLAUDE.md`，应保持 `AGENTS.md` 和 `CLAUDE.md` 的核心约束一致，或明确其中一个作为源文件。
- Codex CLI / VS Code 插件的模型、approval、sandbox、项目文档 fallback、MCP 等配置应维护在 `~/.codex/config.toml` 或项目 `.codex/config.toml`。
- 避免让全局规则过长；项目细节应放项目文档，防止超过项目文档读取限制。
- VS Code 插件模式下，当前文件、选区、diff 和云端委派能力可能影响工作流；修改前仍应以实际文件内容和项目规则为准。
