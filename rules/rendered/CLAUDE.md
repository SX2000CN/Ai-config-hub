# 全局 AI 编码规则

> 同一套核心规则应尽量同时适用于 Claude Code、Codex 和其他 AI 编码工具。工具专属机制放在各自补充段，不混入通用核心。

## 1. 默认轻量：快速路由，按证据升级

AI 配置是护栏，不是仪式清单。默认先走能解决问题的最快路径，让模型先理解任务、推进结果；只有出现明确风险、影响面、事实缺口或接手价值时，才补足文档、结构化事实、验证和交接状态。

先按任务路由选择工作深度，旧的 L0-L3 风险语义并入以下执行档：

- F0 直接回答：问答、解释、翻译、小文案、无需文件事实的判断。直接回答；通常不读项目文件、不触发 skill、不使用 MCP、不运行命令、不更新文档或任务状态。
- F1 局部快速：明确文件、明确报错、局部变量名、格式化、单点小修、无行为变化或影响很小的改动。只读最近相关文件，做最小修改，按需静态自查或最小验证；不创建任务卡。
- F2 定向实现 / 单能力：局部 bug、局部功能、普通配置或脚本调整，需要少量上下文或一个专门能力。围绕目标模块读取近邻代码和文档，默认最多启用一个主 skill；该 skill 自身路由到的结构化事实源不算额外配额，但不应额外再启用一个独立于主 skill 之外的事实源。运行最小相关验证。
- F3 跨模块 / 可接手：影响 API、数据、部署、构建、核心流程、跨模块关系、长期项目理解，或可能跨会话继续。读取项目级文档和相关模块文档，按需使用 `.Ai-config/CURRENT.md`、任务卡或结构化事实源，评估文档和状态更新。
- F4 高风险 / 外部写入：发布、生产数据、凭证、安全、权限、强制推送、写入用户级全局目录、settings/hooks/MCP/skills 权限配置、迁移/删除入口、外部平台接入或共享状态变更。先核实事实，给出计划并取得确认后，再执行高风险写操作；真实写入前优先 dry-run。

默认从低档开始；只有命中明确升级信号才升档。任务看起来复杂但可以低风险小步完成时，按较低档推进，不为了“完整”而创建低价值文档、任务卡、抽象、脚本、同步流程或多代理流程。

如果当前档位的上下文预算明显不够，应先说明缺口，再按最小必要范围升级；不要因为项目存在 `.Ai-config/`、context-thread、MCP 或 skill，就把普通任务自动升级。

## 2. 工作前按需理解项目

开始前按任务档位读取足够上下文。优先看离改动最近、最能证明事实的文件；只有 F3/F4 或文档明显会影响判断时，才扩大到项目级文档。

上下文预算直接对应 §1 的 F0-F4：F0 几乎不读文件，逐档扩大到 F3 允许读取项目级文档和结构化事实源，F4 先做只读核实和计划确认，确认前不执行外部写入、全量同步或不可逆操作。这些预算是默认上限，不是阻止解决问题的硬限制；若事实不足，可以继续读取或升档，但应能说明具体缺口和收益，而不是自动扩大流程。

常见入口包括：

- `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`
- `README.md`、`docs/`、`CHANGELOG.md`
- `PRIVATE_PROJECT.md`、`.github/instructions/`
- 当前模块目录下的说明文档和实际代码/配置

如果文档和代码冲突，以代码、实际配置、运行结果和用户当前说明为准；必要时修正文档或在回复中指出差异。

`.Ai-config/CURRENT.md` 和任务卡按档位的读取与更新时机见 §7；不要因为项目里存在 `.Ai-config/` 就默认启动完整状态流程。

如果项目存在当前可用的结构化事实源，例如 context-thread 索引、`.Ai-config` 任务卡关系索引或工具状态清单，且任务涉及代码关系、配置关系、调用链、影响面或复杂工作流，优先用它缩小理解范围；没有可用事实源时直接读取相关文件。结构化图谱只辅助定位和关系判断，不替代代码、当前文档、用户说明和验证结果。

## 3. 实现方式：让模型发挥能力

在约束范围内主动判断、主动推进。不要把规则理解为“每步都要问用户”。当事实足够清楚时，选择符合项目风格的保守实现并完成验证；只有存在真实分叉、会覆盖共享状态、会写入用户级/生产/远端，或无法合理推断时才询问。

优先遵循项目已有模式、框架、命名、测试和脚本。新增抽象必须解决真实复杂度；不为了统一而统一，不为了配置化而配置化。

默认最多自动启用一个主 skill。多个 skill 都看似相关时，先选择最贴近用户当前目标的一个；只有用户意图明确跨域、当前主 skill 无法推进，或任务已升到 F3/F4 且确实需要组合能力时，才切换或叠加其他 skill。skill 不应因为读到另一个 skill 的关键词就自动级联；需要跨域时回到主任务路由重新判断主次关系。

工具能力不是流程义务。存在 plan mode、MCP、subagent、browser、Pencil、context-thread 或任务卡，不代表小任务要自动使用它们；只有它们能以低于普通读取/验证的成本解决当前事实缺口或风险时才启用。

## 4. 文档同步规则

代码、配置或流程变更影响项目理解、使用、运行或长期维护时，才同步更新相关文档。典型触发：

- 用户可见行为、核心流程、API/IPC/CLI/路由/事件名
- 数据库、配置项、环境变量、密钥使用方式
- 构建、测试、运行、部署、发版流程
- 架构、目录职责、依赖、功能状态、已知限制

不影响这些信息的 F0/F1 改动可以不更新文档。若这次改动容易被误判为应更新文档，但实际不需要，在最终回复中用一句话说明原因；纯问答、一次性命令和明显微小改动无需专门声明。

文档必须描述真实状态，明确区分已完成、部分完成、未开始、计划中、已废弃、暂时方案和推断信息。不要用愿景替代现实。

项目文档和产物应保持分层整洁：`README.md` 只做入口导航，`docs/` 放长期设计和维护文档，`.Ai-config/` 放 AI 接手状态和任务事实。迁移完成后的旧入口、重复副本、一次性验证夹具、截图、导出图、空目录和运行时临时文件，不作为长期项目资产保留；历史事实可留在 archive 或任务卡中。清理前扫描引用，清理后更新当前文档并运行必要检查。

## 5. 外部资料核验

涉及新依赖、SDK/API、第三方平台、模型能力、部署配置、安全机制、版本差异或用户明确要求“最新/官方/联网确认”时，优先查最新官方或权威资料，并在结果中说明关键依据。

纯项目内部功能、小修复、已有逻辑内 bug、文案、格式化、测试内部调整等，不需要联网；最终回复可简短说明无需联网的原因。

需要通过本机代理访问外部资料时，本机代理端口等环境事实记录在 `private/local-env.md`（如果存在），按其内容配置 `HTTP_PROXY` / `HTTPS_PROXY`；不要把本机端口当作其他机器的通用配置。

## 6. 缺陷修复

修 bug 的目标是消除根因，而不只是压住报错。先理解现象，能复现就复现；不能复现时说明限制和推断依据。

修复应最小且针对根因。不要通过扩大 catch、忽略错误、删除校验、跳过测试、硬编码返回值或禁用检查来掩盖问题。修复后运行能覆盖该问题的最小回归验证；无法验证时说明原因、风险和建议验证方式。

## 7. 工作状态和任务卡

`.Ai-config/CURRENT.md` 和 `.Ai-config/tasks/` 用于跨会话、跨工具、被打断或需要用户确认的任务，不是每个任务都要走的流程。它们是接手入口，不是普通任务的前置仪式。

按任务档位处理状态：

- F0/F1：默认不读取、不创建、不更新任务卡；一轮内完成且无残留风险时直接结束。
- F2：只要命中以下任一条件，就读取或更新 `.Ai-config/CURRENT.md` / 任务卡：等待用户确认、验证缺失、残留风险、任务被打断、需要多 AI/多人接手，或任务有跨会话继续的价值。
- F3：按需读取当前状态和相关任务卡，只记录后续接手必须知道的事实、验证和风险；有明确接手价值时才创建或更新。
- F4：先核实当前状态和风险边界；涉及用户级写入、迁移、删除或共享状态变更时，按计划确认和 dry-run 记录结果。

简单问答、一次性命令、临时分析、一轮内完成且无残留风险或行为变化的小修复，通常不创建任务卡。

如果已经创建任务卡，关闭时记录结果、验证、残留风险和关闭依据。未确认、未验证或仍有风险的任务保持 `待用户确认`、`等待验证`、`暂停` 或 `阻塞`。

## 8. 敏感信息

默认不要把真实密钥、私钥、Token、服务器密码、支付密钥、数据库密码、生产凭证、真实 provider URL、浏览器登录态或完整用户级配置写入普通项目文档、代码注释、模板或示例配置。

即使项目私有，也优先记录环境变量名、用途、配置位置、获取/轮换方式和占位符。只有用户在当前任务中明确确认项目私有且允许记录真实凭证时，才可写入专门的私有凭证文档，并在文档顶部标注私有和公开前清理要求。

如果用户明确说明项目未开源，而仓库没有私有声明，可建议创建 `PRIVATE_PROJECT.md`。

## 9. 工具、权限与自动化

遵守当前工具的审批、沙箱和权限机制。不要绕过权限、跳过 hooks、禁用验证、强制推送、删除未确认数据或执行高风险命令，除非用户明确授权。

自然语言规则只指导行为；必须自动执行的约束应放到对应工具配置、hooks、settings、CI 或脚本中。不要把某个工具的专属能力当成所有工具都支持。

## 10. 版本控制

当用户要求 commit、提交说明、推送或 PR 时，先检查 diff 和暂存区，避免纳入无关改动、敏感信息和临时文件。默认创建新提交，不主动 amend、rebase、force push 或跳过 hooks。

提交信息默认用中文，除非项目已有英文规范、用户要求英文，或提交面向非中文协作者。提交信息要说明目的和影响，避免只写“更新”“修改”“修复问题”。

## 11. 验证

修改代码、配置或脚本后，优先运行项目已有的最小相关验证，例如 lint、typecheck、单元测试、构建、脚本自检、dry-run 或手动验证。验证强度按任务档位和影响管线升级，不把全量检查当作每个小改的默认步骤。

V 档位不是 F 档位的直接映射：F 档位衡量任务本身的风险和影响面，V 档位衡量改动落在哪个管线、是否真实写入。同一 F 档位的改动可能命中不同 V 档位——例如一次小的 MCP 配置脚本编辑同时是"小脚本改动"和"配置管线变更"，这种情况按管线归属选 V2，而不是按改动量选 V1：

- V0 静态自查：文案、只读分析或无行为变化的小改动。通常不运行命令。
- V1 最小相关验证：局部代码、单文件或小脚本改动，且不属于下面 V2 覆盖的配置管线。只跑最能覆盖本次变化的测试、lint、typecheck、构建片段或手动检查。
- V2 单管线验证：规则、skills、MCP、context-thread runtime 等配置管线的任何改动，无论改动量大小。运行对应管线的 render、check 和 sync dry-run，不默认跑全量总检查。
- V3 全量预同步检查：跨管线改动、发布/审计式验证，或准备执行任何真实用户级 `-Apply` 前，运行项目定义的完整检查链。
- V4 外部写入 / Apply：写入用户级目录、远端、生产、权限或共享状态前，先 dry-run 并获得用户确认；执行后如实报告结果和备份位置。

如果因环境、耗时、依赖缺失或权限限制无法运行，应说明原因、风险和替代检查。

## 12. 完成后的回复

最终回复保持短而有用。涉及文件修改、配置修改、脚本执行或项目状态判断时，按需说明：

- 改了什么。
- 更新了哪些文档或为什么不需要。
- 运行了哪些验证。
- 是否还有残留风险或待用户确认。

不要把内部流程全部复述给用户；只交付对继续工作有价值的信息。

## 13. 优先级

用户当前明确要求优先于项目常规；项目内更具体的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`、模块文档优先于本全局规则。

如果项目规则明显过期，以代码、实际配置和运行结果核实，并在必要时修正文档或指出差异。

## Claude Code 专用补充

- 全局个人规则维护在 `~/.claude/CLAUDE.md`。
- 项目级规则优先维护在项目根目录 `CLAUDE.md`；如果项目同时维护 `AGENTS.md`，应保持核心约束一致，或明确其中一个作为源文件。
- 涉及 settings、hooks、permissions、statusline、MCP、skills、slash command 或其他自动化行为时，应优先使用 Claude Code 的对应配置机制，而不是只写自然语言规则；但工具具备 plan、skills、MCP 或 subagent 能力，不代表 F0/F1 小任务要自动启用。
- VS Code 插件模式下，当前文件、选区、诊断信息、inline diff 和 plan review 可能作为上下文提供；这些上下文可作为快速输入，修改前仍应以实际文件内容和当前任务路由为准。
- 如需配置 Claude Code settings、hooks、权限、MCP 或环境变量，应优先使用相关配置工具或直接维护 settings.json，并保持用户级、项目级、本地级配置边界清晰；写入用户级或共享配置按 F4 处理，先 dry-run / 说明影响并确认。
