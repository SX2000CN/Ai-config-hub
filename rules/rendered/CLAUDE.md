# 全局 AI 编码规则

> 同一套核心规则应尽量同时适用于 Claude Code、Codex 和其他 AI 编码工具。工具专属机制放在各自补充段，不混入通用核心。

## 1. 核心目标：代码、配置、文档保持一致

默认把项目文档视为项目的可读索引和事实来源。对于长期维护项目、多人协作项目、生产项目和私有维护项目，代码、配置、部署、数据库、接口、用户流程或核心行为发生实质变化时，必须同步评估并更新相关文档。

目标是：任何人、任何 AI 编码工具、任何后续维护者，只要阅读项目中的文档，就能准确理解项目的当前状态、架构、功能、运行方式、部署方式、核心流程、已知限制和后续计划。

对于临时实验、小型脚本、格式化、局部变量重命名、内部无行为变化重构、测试内部实现调整、生成文件变动等不影响项目理解和使用方式的修改，可以不更新文档，但最终回复中应说明无需更新文档的原因。

如果用户明确要求只做临时代码实验或只做一次性验证，可以暂不更新长期文档，但必须在回复中说明这是临时例外。

## 2. 工作前按需理解项目

开始修改前，按任务复杂度快速查找并阅读相关说明文件，例如：

- `AGENTS.md`
- `AGENTS.override.md`
- `CLAUDE.md`
- `README.md`
- `docs/`
- `CHANGELOG.md`
- `PRIVATE_PROJECT.md`
- `.github/instructions/`
- 当前模块目录下的说明文档

小型局部修改只需阅读最相关的文档和代码；跨模块、配置、部署、数据库、API、用户流程或架构变更，则必须阅读项目级文档和相关模块文档。

如果文档和代码冲突，不要盲信文档；以代码、实际配置、运行结果和用户当前说明为准，并在必要时修正文档或在回复中指出差异。

如果项目存在 `docs/ai/CURRENT.md`，开始非简单任务前应先读取它，用于恢复当前工作现场。如果项目同时存在 `docs/ai/tasks/` 或等价任务状态目录，应按 `CURRENT.md` 指引读取对应任务卡。切换任务、暂停任务、完成一轮工作、发现阻塞或验证状态变化时，应刷新 `CURRENT.md` 和相关任务卡，使其他 AI 编程工具或后续会话能直接接手。AI 不得在未确认或未记录风险的情况下丢弃有接手价值的状态；若一轮工作已完成但用户尚未确认，应保持为待用户确认或等价状态。若项目规则允许关闭任务，也必须在状态文件中保留结果、验证情况、残留风险和关闭依据。

## 3. 外部资料核验规则

当任务涉及新依赖、SDK 或 API 接入、第三方平台、模型能力、部署配置、安全机制、版本相关行为，或新功能依赖外部工具、框架、服务的当前用法时，AI 必须优先查阅最新官方文档或权威资料，不得仅依赖模型训练记忆。

如果用户明确要求“最新资料”“联网确认”“官方文档”，也必须优先联网或查阅用户指定资料。

如果当前工具具备联网能力，应先联网核验关键事实，例如接口用法、版本差异、配置项、限制、迁移要求、安全注意事项和官方推荐实践。实现方案和最终回复中应说明关键依据，必要时附上资料来源。

如果当前工具无法联网，应明确说明限制，并请求用户提供资料、开启联网工具，或确认是否继续基于现有项目文件和用户说明处理。

对于纯项目内部的新功能、小修复、格式化、重命名、已有逻辑内的 bug 修复、文案调整、测试内部实现调整等不依赖外部最新信息的任务，可以不联网，但最终回复中应说明无需联网的原因。

## 4. 缺陷修复规则

缺陷修复的目标不是让当前报错消失，而是消除导致错误行为的根因，并防止同类问题再次发生。

当任务是修复 bug、异常、测试失败、线上问题、回归问题或用户反馈的错误行为时，应先理解或复现问题，再定位直接原因和根本原因；不能复现时，应说明环境限制、缺失信息或推断依据。

修复应针对根因做最小正确修改，避免顺手重构或扩大范围；不要通过扩大 catch、忽略错误、删除校验、跳过测试、硬编码返回值、禁用检查等方式掩盖问题。若只能临时缓解，必须标注为临时方案并说明后续根因修复。

修复后应优先运行能覆盖该问题的最小回归验证，例如测试、用例、断言、脚本自检或手动验证步骤；如果无法验证，应说明原因、风险和建议的后续验证。最终回复应简要说明问题表现、根因、修复方式、验证结果和残留风险；若缺陷暴露出文档、配置、流程或测试覆盖不一致，应同步更新相关文档，或说明无需更新的原因。

## 5. 文档更新规则

代码、配置或流程变更必须同步评估文档影响。只要变更影响项目理解、使用、运行或长期维护信息，就必须更新相关文档，尤其包括：

- 项目用途、产品定位、用户流程
- 架构、目录结构、模块职责
- API、IPC、CLI、路由、事件名、数据流
- 数据库表结构、迁移、字段含义
- 配置项、环境变量、密钥使用方式
- 构建、测试、运行、部署、发版流程
- 依赖、技术栈、版本要求
- 重要功能状态：已完成、部分完成、未开始、已废弃、计划中
- 关键限制、风险、注意事项、排障方式

如果变更不影响用户可见行为、接口、配置、部署、数据结构、运行方式或长期维护信息，可以不更新文档，但最终回复需说明原因。

不要为了满足文档要求创建低价值文档；优先更新已有、会被维护者实际阅读的文档。

如果项目缺少文档索引，且本次变更影响项目理解、运行、部署、API、配置或核心流程，应优先更新现有文档；没有现有文档时，可以建议或创建合适的索引文档，例如 `README.md`、`docs/README.md` 或 `docs/项目索引.md`。

## 6. 文档必须描述真实状态

文档不能写成愿景替代现实。必须明确区分：

- 已完成
- 部分完成
- 未开始
- 计划中
- 已废弃
- 暂时方案
- 推断信息

不要夸大完成度。不要写“已完成”来描述代码中尚不存在的能力。

如果某个信息来自推断，而不是代码、配置、运行结果或用户明确说明，必须标注为推断。

## 7. 项目文档应覆盖的内容

项目文档应优先覆盖会影响理解、运行、维护和交接的信息，例如项目用途、技术栈、关键目录、核心流程、接口或配置、开发构建测试命令、部署发版方式、功能状态、已知限制和重要设计决策。

文档应清晰、准确、可验证：

- 使用明确的文件路径、入口函数、命令和配置名
- 不重复粘贴大段代码，只解释结构、流程和约定
- 长期文档可以包含“最后更新时间”或“最后核验时间”；仅当项目已有该约定，或文档内容发生实质更新时同步更新
- 阶段性文档必须标注当前进度
- 文档中的命令应尽量可直接执行
- 中文项目优先使用中文说明，除非项目已有英文规范
- 不保留已经过期的旧流程，除非明确标为历史记录

## 8. 敏感信息默认规则

默认不要把真实密钥、私钥、Token、服务器密码、支付密钥、数据库密码、生产凭证等敏感信息写入普通项目文档、代码注释或示例配置。

即使项目是私有项目，也优先记录凭证用途、环境变量名、配置位置、获取方式、轮换方式和占位符，不记录真实值。

只有当用户在当前任务中明确确认“这是私有项目，可以记录真实凭证”，并确认该文档不会公开、共享、截图或上传时，才允许把真实凭证写入专门的私有凭证文档，例如：

- `docs/private/凭证与密钥.md`
- `docs/deploy/凭证与密钥.md`
- 项目已有的私有运维文档

写入真实凭证时必须遵守：

1. 在相关文档顶部写明：`本项目未开源，文档可能包含真实凭证，仅限私有维护使用。公开、共享、截图或上传前必须清理敏感信息。`
2. 密钥、Token、服务器账号、支付配置等应集中记录，不要散落在 README、架构文档、部署文档、代码注释等多个位置。
3. 普通说明文档可以引用“见凭证文档”，不要重复粘贴完整密钥。
4. 修改相关配置、服务、域名、支付、部署流程时，必须同步检查凭证文档是否过期。
5. 如果项目未来准备开源、交给第三方、上传公开仓库、发布截图或导出文档，必须先清理真实凭证，并建议轮换已暴露凭证。

如果用户明确说明项目未开源，而仓库中没有私有声明，应建议创建 `PRIVATE_PROJECT.md`。

## 9. 工具、权限与自动化

遵守当前工具的审批、沙箱和权限机制。不要绕过权限、跳过 hooks、禁用验证、强制推送、删除未确认数据或执行高风险命令，除非用户明确授权。

自然语言规则只负责指导行为；如果某个行为必须自动执行，应使用对应工具的配置、hooks、settings、config 文件或 CI 机制实现。

不要把某个工具的专属能力当成所有工具都支持。使用 IDE 插件时，可以利用当前文件、选区、诊断信息和 diff 能力，但修改前仍应以实际文件内容为准。

全局规则只规定通用工作方式，不应包含某个具体项目的架构、路径、命令、服务名或业务事实；项目事实应放在项目内文档。

## 10. 版本控制与提交规则

当用户要求创建 git commit、准备提交说明、整理变更记录或提交到远端仓库时，应优先使用中文提交信息，除非项目已有明确的英文提交规范、用户明确要求英文，或提交需要面向非中文协作者。

提交信息应简洁描述本次变更的目的和影响，避免只写“更新”“修改”“修复问题”等无法判断内容的泛化描述。创建提交前应检查当前 diff 和暂存区，避免把无关改动、敏感信息、临时文件或用户未确认的内容纳入提交。

默认创建新的提交，不主动 amend、rebase、force push 或跳过 hooks；涉及改写历史、推送远端、创建 PR、发布版本等会影响共享状态的操作，应先获得用户明确授权。

## 11. 修改代码时的检查清单

实现或修复时，持续检查本次改动是否触发第 5 节的文档更新规则。只要变更会影响用户可见行为、接口契约、配置、数据含义、部署构建测试流程、模块职责或已有文档描述，就同步更新相关文档。

修改代码、配置或脚本后，应优先运行项目已有的最小相关验证，例如 lint、typecheck、单元测试、构建、脚本自检或 dry-run；如果因环境、耗时、依赖缺失或权限限制无法运行，应在最终回复中说明原因和替代检查。

## 12. 完成工作后的回复要求

对涉及文件修改、配置修改、脚本执行或项目状态判断的任务，最终回复中应按需简要说明：

- 改了哪些代码或配置
- 更新了哪些文档
- 如果没有更新文档，说明原因
- 运行了哪些验证命令
- 是否还有文档和代码不同步的残留风险

## 13. 优先级

项目内更具体的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`、模块文档或用户当前明确要求，优先于本全局规则。

如果项目内规则与全局规则冲突，遵循项目内规则；如果项目内规则明显过期，应以代码和实际配置核实，并在回复中指出。

“代码、配置、文档保持一致”始终是默认要求，除非用户明确要求只做临时代码实验。

## Claude Code 专用补充

- 全局个人规则维护在 `~/.claude/CLAUDE.md`。
- 项目级规则优先维护在项目根目录 `CLAUDE.md`；如果项目同时维护 `AGENTS.md`，应保持核心约束一致，或明确其中一个作为源文件。
- 涉及 settings、hooks、permissions、statusline、MCP、skills、slash command 或其他自动化行为时，应优先使用 Claude Code 的对应配置机制，而不是只写自然语言规则。
- VS Code 插件模式下，当前文件、选区、诊断信息、inline diff 和 plan review 可能作为上下文提供；修改前仍应以实际文件内容为准。
- 如需配置 Claude Code settings、hooks、权限或环境变量，应优先使用相关配置工具或直接维护 settings.json，并保持用户级、项目级、本地级配置边界清晰。
